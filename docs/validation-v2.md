## 真实模型请求

新管理器的独立端口和正式端口各运行一次两阶段图片工具测试，合计 **4/4 HTTP 200，4/4 response.completed**：

1. 18 张原始图片（请求约 48.7 MB）通过代理，模型返回预期的只读图片工具调用。

正式实例两次总耗时约 12.39 秒和 6.93 秒，属于单次上游观测，不作为性能基准。没有重放 Blender 写操作。

## 最终同轮性能对照

下表来自一次完整的 v1 对最终 v2 A/B，未跨不同轮拼接数字。相同机器、图片参数、真实 18 图样本和模拟上游，交替 A/B 次序，不包含模型推理。

| 指标 | v1 | 最终 v2 |
| --- | ---: | ---: |
| 1 MiB 纯文本请求中位，40 对 | 5.549 ms | 4.806 ms |
| 4 MiB 纯文本请求中位，40 对 | 23.096 ms | 20.299 ms |

热缓存请求约快 46%，所有 15 个 v2 热样本均为零 Base64 解码、零编码、零输入/输出转移复制。代价是冷缓存请求增加约 191 ms。这里的冷缓存指新建应用缓存，并非冷启动整个操作系统。

保留 Worker 的依据是明显降低图片处理对其他 SSE 连接的阻塞，并不是声称 Worker 让所有请求都更快。图像上游最终字节和模型回答质量仍使用原有默认 1280 / JPEG 80 策略。

## 配置与边界

- `config.json` 保留用户原值，新字段使用默认值。24 MiB 仍是本地发送预算，不是 GitHub 的已验证上限。
- `maxImageQueueMiB=256` 限制活动及排队图片请求的输入字节，并不是进程 RSS 上限；满时返回本地 503，没有发送上游。
- 无图快速通道不再在代理内校验 JSON，原始字节交给 copilot-api 校验；Unicode 转义或图片候选走正常解析。
- 最新包无法在线确认时启动失败，不自动使用旧缓存。启动过程中不升级正在运行的实例。
- 当前命令定位跟随上游实际语法：前置全局参数使用 `--api-home=PATH start`；分离形式应写 `start --api-home PATH`。不会为修正上游不接受的语法重排参数。
- Windows 用户控制管道仅允许服务所属用户；Codex 的独立沙箱身份无法直接访问，需要以用户权限运行启停脚本。

此次是有限场景验收，没有证明所有未来 copilot-api 版本都无需适配，也没有进行持续数小时的并发稳定性测试。
